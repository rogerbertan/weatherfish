# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Estado do projeto

WeatherFish é um app Android de estudo em Kotlin. As Fases 0 a 5 estão prontas, e a Fase 6 está implementada. As telas mostram dados reais da Xweather pelo SDK Aeris. A aba Mapa mostra um mapa Mapbox com as camadas de temperatura e de vento em partículas do MapsGL, centralizado na cidade ativa. O app abre com o clima do local do aparelho, e a busca e as favoritas trocam a cidade ativa. A tela Compartilhar mostra o QR da cidade ativa e lê o QR de outro aparelho de dois jeitos: com o Google code scanner ou com a câmera do app, feita com CameraX e ML Kit. Toda tela abre por um deep link `weatherfish://`, e a navegação interna usa esses mesmos links. Os dados falsos de `app/src/main/assets/fake/` voltam com a flag `DataSourceConfig.useFake`. O projeto tem um único módulo, o `:app`. A `WeatherFishApplication` é anotada com `@HiltAndroidApp` e inicializa o SDK no `onCreate` com `XweatherSdk.init()`. A `MainActivity` é anotada com `@AndroidEntryPoint`, chama `WeatherFishApp` e repassa os deep links que chegam pelo `onNewIntent`. O package e o namespace são `dev.rogerbertan.weatherfish`.

O projeto usa um módulo só por escolha. Não crie módulos Gradle novos. As camadas ficam separadas por pacote dentro de `dev.rogerbertan.weatherfish`:
- `domain` guarda os modelos `GeoPoint`, `Place`, `CurrentWeather`, `HourlyForecast`, `DailyForecast`, `WeatherCondition` e `TemperatureUnit`, este no próprio `TemperatureUnit.kt`. Guarda também as interfaces `WeatherRepository`, `ActiveLocation`, `UserPreferences` e `QrScanner`, mais a `sealed class WeatherError`, que estende `Exception`. Não importa nada de Android.
- O `PlaceQrCodec` de `domain` monta o link do QR, `weatherfish://place?name=...&lat=...&lon=...`, só com `java.net`. Ele não tem um parser de URI próprio: quem lê o link é o Navigation, e o codec só valida os parâmetros com `fromParams`. O `fromParams` devolve um `SharedPlace` ou `null`, e não lança `WeatherError`, porque não é falha de repositório. Ele rejeita nome vazio, nome com mais de 100 caracteres, nome com caracteres de controle ou de formatação, como `\n` e `U+202E`, e coordenada fora da faixa. O `isPlaceLink` diz se um texto lido pelo scanner é um link `place` com até 512 caracteres. O `encode` corta o nome em 100 caracteres e continua cortando até o conteúdo codificado caber em 512, porque um acento vira 6 caracteres na URL. As chaves `NAME_PARAM`, `LATITUDE_PARAM` e `LONGITUDE_PARAM` têm de ser os nomes dos campos da `ImportPlaceRoute`, e o `ImportPlaceRouteTest` falha se divergirem.
- O `QrScanner.scan()` devolve o texto lido, `null` quando o usuário fecha o scanner, ou lança `QrScanException`.
- O `select` e o `useCurrentLocation` da `ActiveLocation` não são `suspend`. A implementação roda o trabalho num escopo de aplicação, porque a tela costuma voltar logo depois da chamada e o `viewModelScope` seria cancelado no meio. O `select` cancela um `useCurrentLocation` pendente, para que a localização não sobrescreva a escolha do usuário quando chegar.
- O `WeatherRepository` devolve os dados direto e lança `WeatherError` quando falha, como um service do Spring. Não crie tipos de resultado como `Result` ou `Either` para o erro.
- `data/xweather` guarda o formato cru da API e o mapeamento para o domínio. As classes com sufixo `Response` são as que vêm da API, como `XweatherResponse<T>`, `ConditionsResponse`, `ForecastResponse` e `PlaceResponse`. As classes aninhadas não levam sufixo. Não use `Dto` no nome. Não crie classes `*Request`, porque a Xweather só recebe GET com query params.
- `data/xweather` também guarda o adapter do SDK Aeris, cujo pacote é `com.aerisweather`. É o único pacote que importa o SDK Aeris. O `XweatherWeatherRepository` roda `AerisCommunicationTask(context, request).executeSyncTask()` dentro de `withContext(Dispatchers.IO)`. Não use `execute()` com callback, porque ele passa pelo executor serial do `AsyncTask` e devolve o resultado na main thread. O `AerisMapping.kt` converte os models do SDK Aeris para o domínio. Os tipos do SDK Aeris têm os mesmos nomes das classes do pacote, então o `AerisMapping.kt` os importa com alias, como `ConditionsResponse as AerisConditionsResponse`.
- O `XweatherSdk` é o único lugar que lê `XWEATHER_CLIENT_ID` e `XWEATHER_CLIENT_SECRET` do `BuildConfig`. Ele usa o overload `initWithKeys(id, secret, appId)`, que não faz rede nem disco no startup. Ele também desliga o log do SDK Aeris com `LogLevel.NONE`, porque o SDK grava no logcat a URL com o `client_secret` quando um request falha. Com as chaves vazias, o repositório lança `Unauthorized` sem fazer request.
- O `weatherErrorFor(code)` traduz os códigos de erro da Xweather e do SDK para `WeatherError`. O SDK Aeris devolve `"IOException"` para qualquer falha de HTTP, inclusive um 401 de chave inválida, e o `weatherErrorFor` traduz esse código para `Network`. Nunca logue nem exiba a `description` dos erros do SDK Aeris, porque ela pode conter a URL com o `client_secret`.
- A busca real tira os acentos do termo com `foldForSearch` antes de enviar, porque a Xweather não encontra `são paulo`. O SDK Aeris não codifica a URL, então a busca também descarta qualquer caractere que não seja letra, dígito, espaço, `-` ou `'`.
- O `parsingOrThrow` de `XweatherMapping.kt` converte as exceções de parsing em `WeatherError.Unknown`. O fake e o repositório real usam o mesmo helper. Os detalhes da API estão em `docs/aeris-spike.md`.
- `data/fake` guarda o `FakeWeatherRepository`. Ele lê os JSONs de `assets/fake/`, um por endpoint, e reaproveita as classes de `data/xweather`.
- `data` também guarda a `DeviceActiveLocation`. Na primeira coleta, ela emite na hora a última localidade salva, ou o `defaultPlace`, que é São Paulo. Em seguida chama `useCurrentLocation()`. Essa função busca a localização atual com o `LocationProvider` e o `placeAt`. Quando a resposta chega, ela troca a localidade. Um `compareAndSet` garante que só o primeiro coletor dispara essa busca. O `isLocating` fica verdadeiro enquanto a busca roda. Cada troca é salva como última localidade.
- `data/location` guarda o `LocationProvider` e o `FusedLocationProvider`. O `FusedLocationProvider` usa a `lastLocation` quando ela tem até 10 min. Senão, pede uma localização nova com timeout de 10 s. Se o timeout passar, usa a `lastLocation` antiga. Ele devolve `null` sem a permissão `ACCESS_COARSE_LOCATION` ou quando há erro.
- `data/scanner` guarda o `GmsQrScanner`, que adapta a `Task` do Google code scanner com `suspendCancellableCoroutine`. O `GmsBarcodeScanning.getClient` aceita o application context. Por isso o `DataModule` cria o `GmsBarcodeScanner` sem Activity e restringe o formato a QR. O botão voltar do scanner chega como `onFailure` com `MlKitException.INTERNAL`, e não como `CODE_SCANNER_CANCELLED`. Por isso o `GmsQrScanner` trata os dois códigos como fechamento. Os detalhes estão em `docs/qr-comparison.md`.
- `data/settings` guarda o DataStore tipado. O `StoredSettings` é serializado em JSON pelo `SettingsSerializer` e tem as favoritas, a última localidade e a unidade. O `DataStoreUserPreferences` implementa `UserPreferences` e também expõe `lastPlace()` e `saveLastPlace` para a `DeviceActiveLocation`. A identidade de uma favorita é o `point`. O `DataStoreUserPreferences` ignora uma `IOException` na escrita. Quando a leitura lança `IOException`, o flow emite os valores padrão e lê de novo depois de 1 s, em vez de terminar.
- O `CachingWeatherRepository` é um decorator com TTL por chave: condições 10 min, previsão por hora 30 min e diária 1 h. A busca e o `placeAt` não passam pelo cache, e o cache não guarda falhas. Chamadas simultâneas para a mesma chave compartilham um único request. Esse request roda no `@ApplicationScope`, para que o cancelamento de uma tela não cancele o request que outra tela espera. O `CachingWeatherRepository` recebe um `TimeSource`, e os testes usam o `TestTimeSource`.
- O qualifier `@ApplicationScope` fica em `data`, porque `di` já depende de `data`.
- `di` guarda o `DataModule`, que liga cada interface de `domain` à implementação, cria o DataStore e o `@ApplicationScope CoroutineScope`. O `DataSourceConfig(useFake = false)` escolhe o repositório, e o `DataModule` sempre o passa para o `CachingWeatherRepository`. Troque para `true` para voltar ao fake. A latência do fake e a flag `simulatedError` ficam no `FakeConfig` desse módulo. Para ver a tela de erro, troque `simulatedError = null` por um `WeatherError`.
- `ui` guarda o NavHost e a bottom bar em `WeatherFishApp.kt`, o tema em `ui/theme` e os componentes comuns em `ui/common`. Há um pacote por tela: `ui/today`, `ui/details`, `ui/favorites`, `ui/week`, `ui/search`, `ui/map` e `ui/share`.
- Os pacotes de `ui` dependem das interfaces de `domain`, nunca das classes de `data`. O `ArchitectureTest`, escrito com Konsist, falha se `domain` ou `ui` importar algo de `data`, do SDK Aeris, do Gson, do Play Services, do DataStore ou de bibliotecas de rede. Ele também falha se `domain` importar algo de Android ou do ZXing, se um arquivo fora de `data.xweather` importar o SDK Aeris ou se um arquivo fora de `data.xweather` mencionar `XWEATHER_CLIENT`.
- O ML Kit também é proibido em `domain` e `ui`, com uma exceção: o `ui/share/QrCameraView.kt`. Ele é também o único arquivo do app que importa `androidx.camera`. O preview da câmera é uma view e não cabe atrás de uma interface de `domain`, então a leitura pela câmera do app mora na UI. O `ArchitectureTest` encontra o arquivo pelo nome, então renomear o `QrCameraView` exige mudar a constante `CAMERA_VIEW` do teste.
- Do mesmo jeito, o `ui/map/WeatherMapView.kt` é o único arquivo do app que importa os pacotes `com.mapbox`, do Mapbox, e `com.xweather.mapsgl`, do MapsGL. A constante do teste é a `MAP_VIEW`. O MapsGL precisa do `client_id` e do `client_secret`. As duas chaves chegam pela interface `MapCredentialsProvider` de `domain`, que o `XweatherSdk` implementa, e o `MapViewModel` as põe no `uiState`. O `mapCredentials` é `null` com as chaves vazias, e a tela mostra uma mensagem no lugar do mapa.
- O `WeatherMapView` cria o `MapboxMapController` num `DisposableMapEffect` e chama `shutdown()` no `onDispose`. Trocar de aba não destrói a `NavBackStackEntry`, então o lifecycle sozinho não libera o controller. O app adiciona as camadas no `subscribeMapLoaded`, antes da primeira camada `symbol` do estilo, para os nomes das cidades ficarem visíveis. O estilo usa `Projection.MERCATOR`, porque o MapsGL não desenha na projeção globe. A centralização roda num `MapEffect(center)`, e não num `LaunchedEffect`. Antes de a `MapView` se ligar ao viewport, a câmera salva pelo `rememberMapViewportState` sobrescreve um `flyTo`. Um `rememberSaveable` guarda a última coordenada centralizada, para a rotação não desfazer o pan. O vento é o `showWind` do `MapViewModel`, que sobrevive à rotação. Os detalhes estão em `docs/mapsgl-spike.md`.

## Comandos

Use sempre o wrapper (`./gradlew`):

```bash
./gradlew assembleDebug                  # build do APK debug
./gradlew installDebug                   # instala em device/emulador conectado
./gradlew test                           # testes unitários (JVM, JUnit 5)
./gradlew testDebugUnitTest --tests "dev.rogerbertan.weatherfish.ArchitectureTest"         # uma classe
./gradlew testDebugUnitTest --tests "*TodayViewModelTest.should show error*"               # um teste
./gradlew pitestDebug                    # testes de mutação com PIT, relatório em app/build/reports/pitest/debug
./gradlew connectedDebugAndroidTest      # testes instrumentados (exige device/emulador)
./gradlew lint                           # Android Lint
```

## Configuração de build

- AGP 9.5.2 com `compileSdk` e `targetSdk` 37 e `minSdk` 35. O AGP 9 já compila Kotlin, então o `:app` não aplica o plugin Kotlin. Não adicione `kotlin-android`. O plugin `kotlin-compose` define a versão do Kotlin do build, e a versão dele no catálogo é a `kotlin`.
- O Hilt gera código com KSP, declarado como `ksp(libs.hilt.compiler)`. Não use kapt.
- O plugin `kotlin-serialization` usa a mesma versão `kotlin` do catálogo. Ele serve às rotas type-safe do Navigation e ao parsing dos JSONs com `kotlinx-serialization-json`.
- Os ícones vêm de `material-icons-extended`, com a versão definida pelo Compose BOM.
- Os testes usam JUnit 5, com a versão definida pelo `junit-bom`. O plugin `de.mannodermaus.android-junit` liga a JUnit Platform nos testes locais e nos instrumentados. Nenhum teste usa JUnit 4. O `androidx.test:runner`, que o plugin adiciona, ainda traz o `junit:junit` de forma transitiva nos testes instrumentados, porque o `AndroidJUnitRunner` depende dele. Não adicione `junit:junit`, `androidx.test.ext:junit` nem `ui-test-junit4` como dependência direta. Fique na linha 5.x do JUnit. A troca para a 6.x só acontece se o usuário pedir.
- Os testes de mutação usam o PIT pelo plugin `pl.droidsonroids.pitest`, o fork do plugin do PIT para Android, com o `pitest-junit5-plugin`. As versões `pitest`, `pitestJunit5` e `pitestGradle` ficam no catálogo. O PIT muta o bytecode e só roda os testes locais. O bloco `pitest` do `app/build.gradle.kts` exclui o código gerado pelo Hilt e pelo kotlinx-serialization, o `di`, o tema e os arquivos que só têm Composables, porque nenhum teste local os cobre. Por isso o `nextCameraRefusal`, que mora no `CameraScanScreen.kt`, fica de fora, assim como o `WeatherMapView`. O `ArchitectureTest` também fica de fora, porque o Konsist lê o código-fonte e não mata mutantes. O `avoidCallsTo` descarta mutações nas chamadas que o compilador Kotlin gera, como `Intrinsics` e `ResultKt.throwOnFailure` da máquina de estados das coroutines. Ainda sobram mutantes falsos de `return null` em `invokeSuspend`, `emit` e `collect`. Só o plugin Kotlin da Arcmutate, que é pago, filtra esses casos.
- O Compose BOM está em 2026.09.00. O Compose 1.13, que vem nos BOMs mais novos, exige `compileSdk` 37.1, e esta máquina só tem a plataforma `android-37.0`.
- Dependências e plugins ficam no version catalog `gradle/libs.versions.toml` e são referenciados como `libs.*`. Adicione novas dependências lá, não com strings inline.
- `settings.gradle.kts` usa `RepositoriesMode.FAIL_ON_PROJECT_REPOS`: repositórios só podem ser declarados lá, nunca em `build.gradle.kts` de módulos. O repositório do Mapbox aceita só os grupos `com.mapbox.*`, e o JitPack só o `com.github.vaisala-xweather`, com `includeGroupByRegex` e `includeGroup`. O repositório do Mapbox entrega a v11 sem token secreto.
- O mapa usa o MapsGL `v1.8.0` e o Mapbox `11.15.3`, na variante `ndk27`, que alinha as `.so` em páginas de 16 KB. O `com.mapbox.maps:android-ndk27` e o `maps-compose-ndk27` usam a mesma versão `mapbox` do catálogo. O POM do MapsGL não declara o Mapbox, então o app escolhe a versão. A `11.15.3` é a que o demo do MapsGL usa. O Mapbox e o MapsGL põem no APK uns 76 MB de `.so` em 4 ABIs, cerca de 20 MB por ABI. As medidas estão em `docs/mapsgl-comparison.md`.
- O carregamento de tiles do MapsGL chama `MapboxMap.executeOnRenderThread` de uma worker thread. O `ThreadChecker` do Mapbox lança `WorkerThreadException` nesse caso, mas só em debug. Por isso o `AndroidManifest.xml` declara a meta-data `com.mapbox.maps.ThreadChecker` com `false`, o que deixa o debug igual ao release.
- Release usa o novo bloco `optimization { enable = true }` do AGP (no lugar de `minifyEnabled`), com regras em `app/src/main/keepRules/rules.keep` (não `proguard-rules.pro`). O `packageScope` limita o R8 a `androidx`, `kotlin` e `kotlinx`. O Gson preenche por reflexão o pacote `model` do SDK Aeris. O `rules.keep` mantém esse pacote para quando o `packageScope` crescer.
- O `app/build.gradle.kts` declara o `aeris-core-lib` com `isTransitive = false`, o equivalente ao `@aar`. O POM dele traz `play-services-maps` e `androidx.test.ext:junit`, que o SDK Aeris não usa. Por isso o `app/build.gradle.kts` declara o Gson à parte.
- O manifest do SDK Aeris pede storage, localização, `READ_GSERVICES` e OpenGL. O `AndroidManifest.xml` do app remove esses itens com `tools:node="remove"`. A exceção é a `ACCESS_COARSE_LOCATION`, que o app declara. A `ACCESS_FINE_LOCATION` continua removida.
- A localização usa `play-services-location` com o `await` do `kotlinx-coroutines-play-services`. As preferências usam o `androidx.datastore:datastore` tipado, não o `datastore-preferences`. A comparação de APK, manifest e dependências antes e depois do Aeris está em `docs/aeris-comparison.md`.
- O `ui/share/QrCode.kt` é o único arquivo que usa o `com.google.zxing:core`. Ele desenha a `BitMatrix` num `Path` com fundo branco fixo. A leitura usa o `play-services-code-scanner`. O `AndroidManifest.xml` declara o meta-data `com.google.mlkit.vision.DEPENDENCIES` com o valor `barcode_ui`. O scanner não pede permissão de câmera ao app. Ele traz o `MlKitInitProvider` e os componentes de telemetria `datatransport`. A comparação antes e depois está em `docs/qr-comparison.md`.
- A câmera do app usa CameraX, com `camera-camera2`, `camera-view` e `camera-mlkit-vision` na versão `camerax`, e o ML Kit `com.google.mlkit:barcode-scanning` bundled. O `camera-lifecycle` chega de forma transitiva pelo `camera-view`. O bundled põe no APK o `libbarhopper_v3.so` de 4 ABIs e soma uns 25 MB ao release. O `AndroidManifest.xml` declara a `CAMERA` e a feature `android.hardware.camera` com `required="false"`. O `camera-view` traz de forma transitiva o `camera-video`, o Media3 e a Guava. O `mlkit:common` traz o `appcompat` de volta. As medidas e a variante unbundled estão em `docs/qr-camera-comparison.md`.
- A UI usa só Jetpack Compose. As bibliotecas de Views `appcompat` e `material` foram removidas. O tema XML `Theme.WeatherFish` só pinta a janela antes do Compose desenhar.
- `local.properties` é específico da máquina, está no `.gitignore` e não deve ser commitado. Além do `sdk.dir`, ele guarda três chaves. `XWEATHER_CLIENT_ID` e `XWEATHER_CLIENT_SECRET` são as credenciais da Xweather e vão para o `BuildConfig` do `:app`. `MAPBOX_ACCESS_TOKEN` é o token público do Mapbox, que começa com `pk.`. Ele vira o `resValue` `mapbox_access_token`, que o Mapbox lê pelo nome em runtime, e por isso o `buildFeatures` liga o `resValues`. Nenhum código referencia esse recurso, e o resource shrinking do release o apagaria. O `res/raw/keep.xml` o mantém com `tools:keep`. Uma chave ausente vira string vazia, e o build passa sem ela.

## Arquitetura com Compose e MVVM

O app tem duas camadas. A camada de UI tem os Composables e o ViewModel, e chama a camada de dados, que tem o Repository e os data sources. Crie uma camada de domínio com use cases só quando mais de um ViewModel reutilizar a mesma lógica. O fluxo é unidirecional. O estado desce do ViewModel para a UI, e os eventos sobem da UI para o ViewModel.

**Faça:**
- Exponha o estado de cada tela numa única propriedade `uiState`. Ela é um `StateFlow` imutável de um tipo imutável. Mantenha o `MutableStateFlow` privado. Use `update` quando o novo estado depender do anterior, como em `update { it.copy(...) }`. Para substituir o estado inteiro, atribua a `.value`.
- Na UI, colete o estado com `collectAsStateWithLifecycle`.
- Receba eventos da UI como chamadas de função do ViewModel.
- Faça a conversão de Flows do repositório para estado com `stateIn` e rode o trabalho assíncrono em `viewModelScope`.
- Mantenha os Composables sem estado e faça state hoisting. Somente o Composable de nível de tela conhece o ViewModel. Os filhos recebem dados e lambdas.
- Use um `Modifier` como primeiro parâmetro opcional dos Composables reutilizáveis.
- Em listas lazy, use o id do item como `key`. Ele precisa ser estável e único.
- Use `remember` só para cálculos caros e `derivedStateOf` para limitar recomposições.
- Exponha os dados do repositório como `Flow` ou funções `suspend`. Eles precisam ser main-safe, e o repositório escolhe o dispatcher.
- Escreva testes unitários do ViewModel isolados da UI.

**Não faça:**
- Não acesse data sources a partir de Composables ou ViewModels. Rede, banco e DataStore só são acessados pelo repositório.
- Não passe ViewModel, `Context`, `Activity` ou `NavController` para Composables filhos, nem guarde nenhum deles dentro do ViewModel.
- Não coloque lógica de negócio em Composables.
- Não exponha `MutableStateFlow` nem `var` público para fora do ViewModel.
- Não escreva num estado que já foi lido na mesma composição. Isso é um backwards write.
- Não use índice nem `hashCode()` como key de lista.
- Não marque com `@Stable` ou `@Immutable` uma classe que não é estável.
- Não use `GlobalScope` nem lance coroutines sem um escopo ligado ao ciclo de vida.
- Não use LiveData em código novo.
- Siga a convenção de arquivos do Kotlin. Agrupe num arquivo só as declarações do mesmo assunto, como `Place.kt` com `GeoPoint` e `Place`, ou `Weather.kt` com a condição e as previsões. Um arquivo com uma classe só leva o nome dela, como `WeatherRepository.kt` e `WeatherError.kt`. Não coloque num arquivo com nome de classe outros tipos sem relação com ela.
- Não escreva nome qualificado no corpo do código, como `java.time.ZoneId.of(...)`. Importe sempre no topo do arquivo, inclusive em mudanças temporárias.

**Padrões já usados no projeto:**
- O estado de carga de uma tela é o `LoadState<T>` de `ui/common`, com os casos `Loading`, `Failed` e `Loaded`. Use o tipo direto, como `LoadState<TodayWeather>`, sem `typealias`. Não use flags booleanas para isso.
- O helper `loadState { }` chama o repositório e converte o resultado em `Loaded`, ou um `WeatherError` em `Failed`. Ele é o único lugar da UI que captura `WeatherError`.
- O `LoadStateContent` desenha os estados `Loading` e `Failed`, este com o botão de retry. A tela só desenha o estado `Loaded`. O `modifier` vai para o `LoadStateContent`, não para o conteúdo.
- Hoje, Semana e Detalhes coletam a `ActiveLocation` no `init` com `combine(activeLocation.place, attempts).collectLatest { ... }` e gravam o resultado num `MutableStateFlow<LoadState<...>>` privado. O `attempts` é um `MutableStateFlow<Int>`, e o `retry()` faz `attempts.update { it + 1 }`. Trocar a cidade recarrega todas as telas na back stack. O estado fica no ViewModel enquanto a tela estiver na back stack, e o cache do repositório evita requests repetidos.
- O `uiState` combina esse estado com a unidade e as favoritas das preferências usando `LoadState.map` e `stateIn(viewModelScope, SharingStarted.Eagerly, ...)`. Trocar a unidade ou favoritar não refaz o request. A temperatura é sempre formatada com `formatTemperature(celsius, unit)`.
- O texto da Busca é um `TextFieldState` no `SearchViewModel`. O ViewModel observa o texto sem espaços nas pontas com `snapshotFlow`, que só emite quando o valor muda. O `onEach` põe o estado em `Loading`, ou limpa os resultados se o termo for vazio. O `debounce` espera 300 ms, ou nada para um termo vazio. O `mapLatest` faz a busca. O `filter` descarta um resultado cujo termo não é mais o atual.
- A permissão de localização é pedida na `TodayScreen` com `rememberLauncherForActivityResult`, uma vez por entrada na back stack. Uma flag em `rememberSaveable` guarda se o pedido já foi feito. Quando o usuário concede, a tela chama `useCurrentLocation()`. O `TodayUiState` tem dois campos: o `content`, do tipo `LoadState<TodayContent>`, e o `isLocating`. Enquanto o `isLocating` for verdadeiro, a barra do topo da Hoje mostra "Buscando sua localização" sem esconder o clima da cidade atual. O item "Minha localização" das Favoritas pede a permissão de novo se ela não estiver concedida. O `LOCATION_PERMISSION` e o `hasLocationPermission()` ficam em `ui/common`.
- As rotas são `@Serializable`. Hoje, Detalhes e Favoritas ficam num grafo aninhado, o `TodayGraph`, para que a aba Hoje continue selecionada nelas. Do mesmo jeito, Compartilhar e a câmera do app ficam no `ShareGraph`. Só o `WeatherFishApp` conhece o `NavController`, e as telas recebem lambdas.
- Toda tela tem um deep link, e toda navegação usa esses links. O objeto `DeepLinks`, em `ui`, é o único lugar com as URIs: `weatherfish://today`, `today/details`, `today/favorites`, `week`, `search`, `map`, `share`, `share/scan` e `place`. Nenhuma tela escreve uma URI na mão. Cada destino declara seu link com `linkTo<Route>(DeepLinks.X)`. Os links de `today` e `share` ficam nos grafos `TodayGraph` e `ShareGraph`, não na `TodayRoute` e na `ShareRoute`, para o `restoreState` da aba funcionar. O `navigateTo(link)` navega com um `NavDeepLinkRequest`. O `navigateToTopLevel(link)` soma `popUpTo` com `saveState`, `launchSingleTop` e `restoreState`. Selecionar um resultado da busca navega para `DeepLinks.TODAY` e volta a pilha até a `TodayRoute`. Sem esse `popBackStack`, o `restoreState` reabriria Detalhes ou Favoritas. O `popBackStack` continua por tipo.
- O `AndroidManifest.xml` aceita o esquema `weatherfish` na `MainActivity`, que tem `launchMode="singleTop"`. Um link chega por dois caminhos:
  - **Abertura a frio.** O `NavHost` lê o `intent` da Activity e chama `handleDeepLink`. Antes disso, o `prepareLaunchLink` da `MainActivity` acrescenta `FLAG_ACTIVITY_NEW_TASK` e `FLAG_ACTIVITY_CLEAR_TASK`. Com as duas flags, o `handleDeepLink` monta a pilha completa sem recriar a Activity, com a Hoje embaixo. Sem `NEW_TASK`, ele só empilharia o destino final, e um diálogo ficaria sem tela embaixo. Sem `CLEAR_TASK`, ele fecharia e reabriria a Activity. Se o `intent` tem `FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY`, o app foi reaberto pelos recentes, e o `prepareLaunchLink` apaga o link para ele não rodar de novo.
  - **App aberto.** A `MainActivity` põe cada `Intent` do `onNewIntent` num `Channel`, e o `WeatherFishApp` chama `openLink`. O `openLink` navega sobre a pilha atual. Ele usa `navigateToTopLevel` para as abas e `navigateTo` para o resto, e ignora um link que o grafo não conhece. Não use `handleDeepLink` aqui, porque com `NEW_TASK` ele recria a Activity e perde o estado das abas. O `Channel` guarda o link até a primeira composição. Isso importa quando o processo morreu e o Android recria a Activity com o estado salvo.
  - Teste um link com `adb shell am start -a android.intent.action.VIEW -d "weatherfish://week" dev.rogerbertan.weatherfish`.
- As setas de Detalhes e Favoritas usam `navigateUp`. Quando o destino atual é um diálogo, que implementa `FloatingWindow`, a bottom bar marca a aba da tela de baixo.
- O link `weatherfish://place?name=...&lat=...&lon=...` é o mesmo conteúdo do QR e abre o diálogo `ImportPlaceDialog`, uma destination `dialog<ImportPlaceRoute>`. O diálogo só fecha pelos botões, e não pelo voltar nem por um toque fora, para não cancelar um salvamento em andamento. Os campos da `ImportPlaceRoute` são `String` com valor padrão, para o Navigation gerar os parâmetros como query e nunca falhar ao converter um número. O `ImportPlaceViewModel` lê os campos do `SavedStateHandle` pelo nome da propriedade e valida com `PlaceQrCodec.fromParams`.
- Qualquer página ou app pode abrir o link `place`, então o diálogo começa em `Confirm` e só salva depois do toque em Salvar. O `save()` confere se o ponto já é favorito e, nesse caso, mostra `AlreadySaved` sem fazer request. Senão, chama `placeAt` dentro do `loadState`, porque o link não traz região, país nem fuso. A favorita salva mantém o nome e o `point` do link, e o `Saved` mostra a região e o país do `placeAt` para o usuário conferir. Abrir o link não troca a cidade ativa. Em `Failed`, o Tentar de novo chama `save()` outra vez.
- O scanner da Compartilhar também passa por esse link. O `ShareViewModel` lê o QR, confere com `PlaceQrCodec.isPlaceLink` e põe o texto lido, sem mudança, no `uiState.scannedLink`. A tela chama `onOpenLink` e depois `linkOpened()`. Assim, o scanner e a câmera nativa passam pelo mesmo parser, o do Navigation. O QR que não é link `place` e a falha do scanner viram um `ShareMessage`, que a tela mostra num snackbar antes de chamar `messageShown()`. O QR da cidade ativa não pode falhar, então o `uiState.qr` é um `SharedQr?`, e não um `LoadState`.
- O botão "Ler com a câmera do app" da Compartilhar abre a `CameraScanScreen`, pelo link `share/scan`. A tela pede a `CAMERA` dentro do `CameraPermissionGate`. O gate nunca salva o "concedido". Ele vem do `checkSelfPermission` na composição e em cada resume, porque revogar a permissão mata o processo e um `Granted` restaurado abriria a câmera sem permissão. O `rememberSaveable` guarda só a recusa, do tipo `CameraRefusal?`, e o `requesting`, que evita pedir de novo quando a tela gira com o diálogo aberto. Sem permissão e sem recusa, a tela pede. O `nextCameraRefusal` decide entre `Denied` e `Blocked`. Um `shouldShowRequestPermissionRationale` falso só significa `Blocked` depois de uma recusa anterior, porque fechar o diálogo sem responder também devolve falso. Em `Blocked`, o botão abre as configurações do app.
- A Compartilhar esconde o botão da câmera quando o aparelho não tem `FEATURE_CAMERA_ANY`. O link `share/scan` abre a tela mesmo assim, e o `QrCameraView` cobre esse caso.
- O `QrCameraView` liga um `LifecycleCameraController` ao `LocalLifecycleOwner`, que é o `NavBackStackEntry`. Assim, a câmera fecha no background e quando a tela sai da pilha. O bind só acontece depois do `initializationFuture`, com a câmera traseira, ou a frontal se não houver traseira. Sem nenhuma, o componente chama `onCameraUnavailable`, e a tela mostra uma mensagem no lugar do preview. Ele só ativa o caso de uso `IMAGE_ANALYSIS`, além do preview, que vem implícito. O `PreviewView` usa o modo `COMPATIBLE`, e o container precisa de `clipToBounds`, senão o preview cobre a barra do topo em paisagem. O componente entrega os códigos de cada frame em `onCodesDetected` e recebe `isAnalyzing`. Quando ele fica falso, o componente chama `clearImageAnalysisAnalyzer()`.
- O `CameraScanViewModel` não tem dependências. Ele só aceita um código visto em `CONFIRMATION_FRAMES` frames seguidos, e prefere o link `place` quando o frame tem vários códigos. Ao confirmar um link `place`, ele põe o link no `scannedLink` e desliga o `isAnalyzing` para sempre. Um código que não é `place` vira `ShareMessage.InvalidCode` uma vez por aparição. A tela abre o link com `popUpTo<CameraScanRoute> { inclusive = true }`, então o diálogo de importação fica sobre a tela que estava embaixo da câmera, e não sobre a câmera. Não use `popUpTo<ShareRoute>`. Quando a câmera abre pelo link com o app aberto, o Navigation não empilha a `ShareRoute`, e o pop é ignorado. A navegação para `share/scan` usa `launchSingleTop`, para um segundo link não empilhar outra câmera.
- O Navigation decodifica a query com `Uri.decode`, que não converte `+` em espaço. Por isso o `PlaceQrCodec.encode` gera `%20` nos espaços, e um `+` no link chega como `+` no nome.

## Testes

- Use as anotações e asserções de `org.junit.jupiter.api`. Mocke as dependências com `mockk`, `coEvery` e `coVerify`, do MockK. Não escreva classes stub à mão.
- Para casos de tabela, use `@ParameterizedTest` com `@CsvSource`, como no `XweatherMappingTest`. Não junte vários casos num único `assertEquals` de listas.
- O nome de cada teste segue o padrão `should ...`, entre crases, por exemplo `` `should show error when hourly forecast fails` ``.
- O corpo segue o padrão AAA, separado pelos marcadores `// Arrange`, `// Act` e `// Assert`.
- Nos testes de ViewModel, registre a `MainDispatcherExtension` num campo com `@JvmField @RegisterExtension`. Rode cada teste com `runTest(mainDispatcher.dispatcher)` e avance o tempo com `advanceUntilIdle` ou `runCurrent`.
- Nos testes da Busca, escreva no `TextFieldState` com `setTextAndPlaceCursorAtEnd` e chame `Snapshot.sendApplyNotifications()` em seguida. Fora da composição, o `snapshotFlow` só vê a mudança depois dessa chamada.
- Teste funções puras, como parsing e mapeamento, sobre entradas reais. O `FakeJsonTest` lê os arquivos de `src/main/assets/fake/` direto do disco.
- Os dados de teste compartilhados ficam em `ui/TestData.kt`, no source set de teste.
- Nos testes de classes que recebem um `CoroutineScope`, como a `DeviceActiveLocation`, passe o próprio `TestScope`. O `advanceUntilIdle` não roda tarefas que ficam só no `backgroundScope`. Se a classe usar `async` e o teste esperar falhas, use `CoroutineScope(coroutineContext + SupervisorJob())`, como no `CachingWeatherRepositoryTest`. Assim uma falha não cancela o teste.
